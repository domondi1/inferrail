# 0011. A second, A2A-transport hosted capability, with recovery keyed on the buyer's own payment nonce

## Status

Accepted

## Context

Inferrail Economic Authority is Inferrail's second hosted, paid
capability: a buyer purchases a durable coordination boundary (a root
delegation with a buyer-declared spending ceiling) that multiple agents
can operate under without double-allocating that authority. Like Work
Economics (ADR 0010), it is additive: it must not change how the OSS
gateway or Work Economics operate, and neither may gain a dependency on
it.

Two design questions this capability faces that Work Economics does not:

1. Work Economics is a single-shot compute-and-receive capability — one
   `POST /invoke` call does everything. Economic Authority's value is a
   *session* an agent operates against over time: reserve, grant,
   consume, settle, and revoke are all separate, individually
   authenticated calls against state that must survive between them, and
   a `reserve` may mint a brand-new credential mid-lifecycle that must
   reach exactly the right caller.
2. A buyer who pays for a session can be charged and then never receive
   (or later lose) the root credential that purchase was supposed to
   produce. Some recovery mechanism is required, and it must actually be
   reachable in the failure case it exists for — not merely appear to be
   in a test suite that never tries the truly-lost-every-response case.

## Decision

**Isolation.** The capability's code lives in a new top-level
`hosted/a2a_economic_authority/` directory, following exactly the pattern
ADR 0010 established: not part of the `inferrail` pip package, not
imported by any gateway or Work Economics code path, its own dependency
set (`a2a-sdk`, `x402`, `cdp-sdk` via the `hosted` extra). `git diff
origin/main -- hosted/work_economics/` stays empty across every commit
that has ever touched this capability.

**A2A transport, not plain REST, for the session's operations.** The
Work Economics shape (one authenticated HTTP call, one response) does not
fit a capability whose entire value is a shared, multi-step, multi-caller
lifecycle. This service exposes its six direct operations
(reserve/grant/consume/settle/status/revoke) over real
[A2A](https://a2a-protocol.org/) JSON-RPC `SendMessage` transport, using
the installed `a2a-sdk` directly rather than a hand-rolled protocol —
bearer capability tokens travel only in the standard `Authorization`
header, never inside a message or task history. Purchasing a session
(`POST /sessions`) and recovering one (`POST /sessions/recover`) remain
plain HTTP, since x402 is an HTTP-native protocol and neither operation
belongs in the A2A message/task history in the first place — a purchase
happens once, before any A2A session exists to send it through, and
recovery must survive even a total loss of A2A-independent HTTP
responses.

**Recovery is keyed on the buyer's own payment nonce, never a
server-generated identifier.** The EIP-3009 `payment_nonce` inside a
buyer's signed x402 payment is generated by the buyer's *own* client
library before that payment is ever sent (`x402.mechanisms.evm.utils
.create_nonce`) — the buyer holds it independent of anything this service
has ever said back. `session_id`, by contrast, is server-generated
(`secrets.token_hex(16)`) and is disclosed to the buyer only in the
purchase response — the exact thing a genuinely lost-response buyer does
not have. An earlier iteration of this capability's recovery mechanism
was keyed on `session_id`, and was consequently unreachable in precisely
the scenario it existed for; this was found, and fixed, in a dedicated
post-implementation economic-correctness review (see
`hosted/a2a_economic_authority/sessions.py`'s and `capabilities.py`'s
module/method docstrings, "Known residual gap" and
`get_session_purchase_for_recovery`, for the full analysis). `payment_
nonce` alone is never sufficient authorization on its own — it is not
secret, since it travels in the buyer's own signed payload and is
disclosed to the facilitator — so a buyer-generated `recovery_secret`
(sent only as a SHA-256 commitment at purchase time, required, not
optional) remains the actual proof-of-knowledge gate.

**Settlement completes before the purchase handler runs.** `POST
/sessions` uses x402's `"upfront"` payment flow rather than the scheme's
default `"authorization"` flow, so a settlement failure can never leave a
session durably created and labeled `"PAID"` for a payment that never
actually landed — see `sessions.py`'s "Settlement-before-handler" section
for the defect this closed and why it is closed structurally, not by
convention.

## Consequences

- A future outage or removal of this capability cannot break `inferrail
  serve` or Work Economics for any existing deployment.
- Any future hosted capability whose value is a multi-step, multi-caller
  lifecycle (rather than one-shot compute) should default to A2A
  transport for its operations, reserving plain HTTP specifically for
  payment and recovery, which are not naturally part of an agent-session
  message history.
- Any future capability with its own recovery mechanism must key
  recovery on information the caller can prove it held *before* the
  request that might be lost — never on an identifier the service alone
  generates and discloses only in a response that could itself be the
  thing that got lost. This capability's own history is the cautionary
  example: getting this backwards produces a recovery mechanism that
  looks correct in tests (which always have the response in hand) while
  being unreachable for real affected users.
- One residual gap remains open by design: a crash between x402
  settlement succeeding and this capability's first durable write has no
  automated recovery, because there is nothing yet to key recovery off of
  when it occurs. Closing it fully would require either trusting
  undocumented facilitator-specific error semantics for a replayed nonce,
  or building direct on-chain reconciliation independent of the
  facilitator — both out of scope for this phase, and the former risks a
  strictly worse failure (an unpaid request obtaining a session) if
  gotten wrong. This is recorded as a blocking prerequisite for any real
  (mainnet) deployment of this capability, not something this ADR treats
  as resolved.
- `hosted/` remains excluded from `mypy`'s `packages` list and the wheel
  build, exactly as ADR 0010 established; this capability is additionally
  type-checked on its own via a dedicated `mypy --strict` invocation in
  CI, since its correctness bar (real money, real credentials) warrants
  it even though the directory as a whole is not part of the installable
  library's public API surface.
